## 区域侧已有用户信息时，union 注册的完整行为

### 调用链路

```
union-access (QueryUnionUserAreaInfo)
  → 查本地 union-area 映射 (QueryUnionUserAreaInfoByUUID)
  → 本地没有 → RegisterUnionUserToArea
    → RequestRegisterAreaUser (HTTP POST → area-servo)
      → area-servo: /v1/servo/register (Register)
```

### 关键代码证据

**1. area-servo 侧：检测到用户已存在，返回 1105 + 已有的 UID**

`area-servo/handler/handler.go:37-44`：

### 总结

| 步骤 | 发生什么 |
|------|----------|
| 1 | union-access 发现本地没有该用户→区域的映射关系 |
| 2 | 向 area-servo 发起 `POST /v1/servo/register` |
| 3 | area-servo 查库发现 third_id 已存在，返回 `errcode=1105` + **已有的 UID** |
| 4 | union-access 识别 1105 为「帐号已存在为正确逻辑」，**不当错误处理** |
| 5 | union-access 用区域返回的 UID 写入本地 `DBUnionUserAreaInfo` 映射表 |
| 6 | 后续流程正常继续，上层调用方无感知 |

**核心结论：区域侧已有用户信息不会导致注册失败。area-servo 返回 1105 时同时会把已有的 UID 带回，union-access 将其视为正常情况，用这个 UID 补全本地缺失的 union↔area 映射关系后继续。**查库已完成。`t_union_user_game_area_storage_info` 是**用户-游戏-区域存档存储信息表**（非注册映射表），结构如下：

| 字段 | 含义 |
|------|------|
| `id` | `{uuid}_{ugid}_{area_type}` 复合键 |
| `uu` | 统一用户ID (UUID) |
| `ug` | 统一游戏ID (UGID) |
| `a` | 区域类型 (AreaType) |
| `ov` | 操作版本 (OpVersion) |
| `os` | 操作状态 (1=pre_game, 2=doing_game, 3=done_game, …) |
| `duv` | 完成 union 版本 (DoneUnionVersion) |
| `dav` | 完成 area 版本 (DoneAreaVersion) |
| `dty` | 完成类型 (1=game, 2=dispatch) |

这个表记录的是**存档迁移**的操作状态，与注册流程中的 `DBUnionUserAreaInfo`（union↔area 用户映射表，UUID+AreaType+UID+State）不是同一张表。

区域侧已有用户信息时，union 注册流程：
